# 아이작 팀 소개 페이지 PRD

| 항목 | 내용 |

PRD는 누구를 위해 어떤 홈페이지를 만들지 정리한 기획서입니다.

## 1. 배경 · 문제
- 아이작은 반복 업무를 자동화하고 고객의 장애 접수를 받는 1인 팀이다.
- 기존 고객은 장애가 생겼을 때 어디로 무엇을 알려야 하는지 쉽게 찾을 수 있어야 한다.
- 새로운 고객은 제공하는 자동화 서비스를 이해하고 문의할 수 있어야 한다.
- 소개와 두 가지 방문 목적을 한 페이지에 모은다. 수업용 가상 팀 소개로 구성한다(가정).

## 2. 목표와 성공 기준
| 목표 | 성공 기준 (측정 방법) |
|---|---|
| 아이작의 역할을 쉽게 이해한다 | 첫 화면에 1인 팀 소개와 자동화 서비스 설명이 보인다 |
| 방문 목적에 맞는 안내를 찾는다 | 첫 화면에서 ‘장애 접수 안내’와 ‘자동화 문의’가 구분되고 각 섹션으로 이동한다 |
| 모바일에서도 사용한다 | 375px 화면에서 가로 스크롤이 없고 메뉴와 버튼을 누를 수 있다 |
| 시연과 실제 접수를 구분한다 | 외부 연결 전에는 실제 접수되지 않는다는 안내가 명확하며 접수 완료 문구를 표시하지 않는다 |

## 3. 대상 사용자
| 대상 | 궁금한 것 | 페이지가 줘야 할 답 | 기대 행동 |
|---|---|---|---|
| 기존 고객 | 장애가 생겼을 때 어떻게 알리나? | 필요한 정보와 접수 경로 | 장애 접수 안내 확인 |
| 새로운 고객 | 어떤 반복 업무를 자동화할 수 있나? | 서비스 3종과 요청 예시 | 자동화 서비스 문의 |

## 4. 범위
**이번에 만드는 것 (In scope)**
- 팀 소개, 자동화 서비스 3종, 장애 접수 안내, 서비스 문의 안내를 담은 한 장짜리 홈페이지.
- 헤더 고정 메뉴, 두 가지 주요 버튼, 모바일 메뉴.
- 실제 연결 전의 접수 경로를 ‘준비 중’으로 표시한다(가정).
- 우리가 만든 도구는 결과물을 임의로 만들지 않고 ‘준비 중’ 카드로 표시한다.

**다음 단계로 남기는 것 (Out of scope)**
- 실제 장애 접수 전송, 고객 로그인, 첨부파일 업로드, 접수번호 발급, 처리 상태 조회.
- 고객 정보 저장과 담당자·고객 자동 알림. 이들은 서비스 소개 대상이며 이번 소개 페이지의 작동 기능은 아니다.
- 운영용 접수는 실제 폼 서비스 또는 서버와 저장소를 연결한 후 제공한다.

## 5. 정보 구조 (메뉴)
| 메뉴 | 섹션 ID | 담는 내용 |
|---|---|---|
| 아이작 소개 | #intro | 팀 한 줄 소개, 1인 팀 안내, 두 가지 주요 버튼 |
| 자동화 서비스 | #work | 엑셀·자료 정리, 정기 보고서, 접수·처리 알림 자동화 |
| 우리가 만든 도구 | #tools | 준비 중 카드; 상단 메뉴에는 생략(가정) |
| 장애 접수 | #support | 장애 전달 시 필요한 정보, 실제 접수 연결 준비 상태 |
| 서비스 문의 | #contact | 자동화 상담을 위한 정보, 예시 문의 경로 |

## 6. 화면 구성 (위에서 아래로)
1. 헤더: 아이작 로고 또는 글자 로고와 4개 메뉴.
2. 첫 화면: 한 줄 소개와 ‘장애 접수 안내’, ‘자동화 문의’ 버튼.
3. 자동화 서비스: 3개 업무 카드와 요청 예시.
4. 우리가 만든 도구: 준비 중 카드.
5. 장애 접수: 고객이 준비할 항목과 연결 준비 안내.
6. 서비스 문의: 상담할 때 알려 줄 항목과 문의 경로.
7. 푸터: 아이작 · 1인 자동화 팀, 시연용 페이지 안내.

## 7. 콘텐츠 상세
### 7-1. 한 줄 소개
- 제목: 반복은 줄이고, 중요한 일에 집중하세요.
- 보조 문구: 아이작은 반복 업무 자동화와 고객 장애 접수를 돕는 1인 팀입니다.
- 버튼: ‘장애 접수 안내’ → #support / ‘자동화 문의’ → #contact.

### 7-2. 업무 카드
| # | 제목 | 설명 | 요청 예시 |
|---|---|---|---|
| 1 | 엑셀·자료 정리 자동화 | 여러 파일을 합치고 중복 자료를 정리하는 반복 작업을 줄입니다. | 매주 받는 엑셀 파일을 하나로 합치고 싶어요. |
| 2 | 정기 보고서 자동화 | 반복되는 집계와 보고서 작성을 자동화합니다. | 매일 같은 양식으로 요약 보고서를 만들고 싶어요. |
| 3 | 접수·처리 알림 자동화 | 접수나 처리 상태 변경에 맞춰 알림을 보내는 흐름을 구성합니다. | 접수 내용과 상태 변경을 자동으로 알리고 싶어요. |

### 7-3. 문의
| 항목 | 값 |
|---|---|
| 장애 접수 준비 항목 | 증상, 발생 시각, 재현 순서, 영향 범위 |
| 자동화 상담 준비 항목 | 반복하는 일, 빈도, 현재 소요 시간, 원하는 결과 |
| 요청 채널 | 준비 중(가정) |
| 이메일 | team@example.com — 예시 주소, 실제 수신 경로로 사용하지 않음 |
| 응답 시간 | 운영 시간 확인 후 안내; 즉시 응답·24시간 지원 등 미확인 약속은 표시하지 않음 |

## 8. 디자인 가이드
| 항목 | 아이작 적용 방식 |
|---|---|
| 배경 | #000000, #09090b; 안내 카드 #18181b |
| 밝은 구간 | 서비스 #fafafa, 문의 #e5e5e5 |
| 글자 | #e5e5e5, 보조 #888, 밝은 구간 #000000 |
| 강조 | 빨강 #ef4444; 주요 버튼, 마침표, 번호, 선택 영역 |
| 영문 제목 | ZTNature 우선, Inter 대체; 약 11.8vw, Black 900과 Thin Italic 300 조합 |
| 글꼴 제공 상태 | ZTNature 원본 파일 미제공. 설치된 local 글꼴만 사용하고 없으면 Inter로 대체 |
| 한글 | Noto Sans KR 또는 시스템 한글 글꼴; 행간 충분히 확보 |
| 본문 | 기본 18~20px, 모바일 15~16px; 300/400 굵기 |
| 하위 라벨 | Space Mono, 약 12~14px; 모바일 축소 |
| 질감 | SVG 노이즈 오버레이, opacity .15, mix-blend-mode overlay |
| 배경 효과 | 사용자 지정 적갈색 radial-gradient와 렌즈를 연상시키는 원형 CSS 그래픽 |
| 스크롤 | 배경 scale 1→1.27, 제목 scale 1→.89, 제목 불투명도 완만한 감소 |
| 등장 전환 | cubic-bezier(.16,1,.3,1), opacity와 translateY |
| 접근성 | 움직임 멈춤 버튼, prefers-reduced-motion 대응, 키보드 포커스 |
| 로고 | 빨간 원형 표시 + ISAAC / 아이작 글자 로고 |
| 참고 스타일 | 사용자의 최신 모노크롬·레드·렌즈 초점 전환 명세 |

### 8-1. 아이작을 위한 구성
- 첫 화면: Less repetition. / More impact. + 한국어 핵심 설명.
- 자동화 문의와 장애 접수 안내를 나란히 배치한다.
- 서비스는 밝은 배경의 3개 아코디언 행으로 구분한다.
- 기존 고객용 장애 안내는 검정 배경, 신규 고객용 문의는 밝은 회색 배경으로 나눈다.
- 준비되지 않은 도구와 실제 수신 경로는 준비 중으로 표시한다.
- 문의·장애 전달 내용은 대화상자에서 작성하고 복사할 수 있으나 저장·전송하지 않는다.

## 9. 반응형 · 접근성
- 휴대폰 375px부터 데스크톱 1280px까지 가로 스크롤이 없어야 한다.
- 서비스 카드: 데스크톱 3열 → 태블릿 2열 → 휴대폰 1열.
- 640px 아래에서 햄버거 메뉴, 휴대폰 좌우 여백 최소 16px.
- 메뉴 버튼에 펼침 상태와 접근 가능한 이름을 제공한다.
- 키보드 포커스 표시, 읽기 쉬운 대비, 이미지 대체 텍스트를 적용한다.
- 움직임 줄이기 설정에서는 부드러운 스크롤 등 불필요한 움직임을 줄인다.

## 10. 기술 조건
- index.html 하나에 HTML·CSS·JavaScript를 포함한다. 이미지는 images/에서 불러온다.
- 빌드 도구나 로그인 없이 파일을 열어 확인할 수 있다.
- 실제 접수 연결 전에는 고객 입력을 외부로 보내거나 수집하지 않는다.
- 사이트는 소유자 전용으로 게시한다. 실제 접수 수신 연동은 다음 단계로 남긴다.

## 12. 완료 기준
- [ ] 메뉴와 주요 버튼이 해당 섹션으로 이동한다.
- [ ] 팀 소개와 서비스 3종이 확정 내용과 일치한다.
- [ ] 실제 접수 연결 상태를 정확하게 안내한다.
- [ ] 준비되지 않은 도구와 접수 경로는 ‘준비 중’으로 보인다.
- [ ] 모바일에서 가로 스크롤이 없고 메뉴가 작동한다.
- [ ] 로고 또는 임시 글자 로고가 헤더에 보인다.
- [ ] 존재하지 않는 실적, 고객 후기, 응답 시간 약속이 없다.

## 13. 열린 질문
- 로고가 별도로 있는가? 현재는 없다고 가정했다.
- ‘아이작’은 수업용 가상 팀 이름으로 사용해도 되는가? 현재는 가상 소개로 기획했다.
- 실제 장애 접수와 서비스 문의는 어떤 외부 폼 또는 채널로 연결할 것인가?
- 운영 시간과 고객 응답 기준은 무엇인가?
- 첫 버전은 접수 안내 페이지로 만들고 실제 전송은 다음 단계로 진행해도 되는가?
- 영문 제목은 제안한 문구를 사용하고, 핵심 서비스 설명은 한국어로 유지한다(가정).
