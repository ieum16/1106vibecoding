# 최초아이디어팀 홈페이지 PRD

> PRD는 홈페이지를 누구를 위해, 왜 만들고, 어떤 내용을 담을지 정리한 설계서입니다.

| 항목 | 내용 |
|---|---|
| 작성일 | 2026-11-06 |
| 문서 상태 | 대화에서 합의한 요구사항 정리 · 완료 기준은 요구사항 기반 검토안 |
| 팀 규모 | 팀장 포함 5명 |
| 구현 | HTML / CSS / JavaScript, 로그인·데이터베이스 없음 |
| 소스 관리·배포 | GitHub에 소스 업로드, Vercel로 배포 |
| 화면 지원 | 휴대폰·태블릿·데스크톱 |

이 문서는 기존 `homepage.md` 이후의 대화에서 확정한 범위를 반영한다. 기존 문서의 실제 공동 사용·승인·공유 저장 구상보다 이 문서의 체험용 범위를 우선한다. 아직 확인되지 않은 사항은 `[준비 필요]`로 표시한다.

## 1. 한 줄 소개

**최초아이디어팀은 세상에 없던 아이디어를 발굴하고, 기획·구현 가능성 검토·시장조사를 통해 실행 가능성을 탐색하는 5인 팀입니다.**

## 2. 목적

1. 새로운 아이디어를 제안할 방법을 안내한다.
2. 평가·보완·승인 과정을 예시 화면으로 보여 준다.

팀의 역할과 프로젝트를 소개하고, 방문자가 제안에 필요한 내용을 이해한 뒤 직접 작성과 검토 과정을 체험할 수 있도록 한다. 실제 업무 접수나 승인 시스템으로 운영하지 않는다.

## 3. 누가 볼지

| 대상 | 필요한 정보 | 홈페이지에서 기대하는 행동 |
|---|---|---|
| 전체 구성원 | 아이디어 작성 항목, 제안 방법, 평가·보완 과정 | 제안 방법을 이해하고 작성·평가·보완을 체험한다. |
| 경영진·리더 | 아이디어 검토·진행·구현 승인 및 비용 협업 부서 지정 흐름 | 예시 화면에서 검토·승인 과정을 이해한다. |

초기에 논의한 실제 평가 공유, 내용 공동 수정, 진행 상황 공동 관리, 구현 승인과 비용 협업 부서 지정은 이번 버전에서는 체험 화면으로만 다룬다.

## 4. 꼭 필요한 기능 — 5개

### 4.1. 팀 소개

- 팀 이름, 한 줄 소개, 팀장 포함 5명이라는 정보를 표시한다.
- 아이디어 발굴·기획·구현 가능성 검토·시장조사 역할을 소개한다.
- 팀원별 닉네임과 역할을 카드로 보여 준다.

### 4.2. 아이디어 제안 안내

- 제안에 필요한 필수·선택 항목과 작성 방법을 설명한다.
- 실제 제출 경로는 `[준비 필요]`로 표시한다.
- 제출 경로가 정해지기 전에는 실제 접수가 가능한 버튼이나 접수 완료 메시지를 제공하지 않는다.

### 4.3. 제안 작성 체험

| 항목 | 구분 | 작성 안내 |
|---|---|---|
| 제목 | 필수 | 아이디어의 핵심을 짧게 적는다. |
| 해결하려는 문제 | 필수 | 누가 어떤 상황에서 겪는 문제인지 적는다. |
| 아이디어 설명 | 필수 | 해결 방식과 핵심 내용을 적는다. |
| 기대 효과 | 필수 | 어떤 변화나 가치를 기대하는지 적는다. |
| 예상 비용 | 선택 | 알고 있는 경우 금액·범위·근거를 적는다. |
| 구현 방법 | 선택 | 알고 있는 기술이나 실행 방법을 적는다. |

- 작성한 내용을 같은 화면에서 미리 볼 수 있다.
- 필수 항목이 비어 있으면 해당 입력란에 쉬운 안내를 표시한다.
- 버튼 문구는 ‘제안 미리보기’ 등 체험임을 알 수 있게 작성한다.
- 입력은 다른 사람에게 전송하거나 공동 저장하지 않는다.
- 저장 방식과 새로고침 이후 유지 여부는 `[준비 필요]`다. 화면에는 실제 동작에 맞는 보관 안내를 표시해야 한다.

### 4.4. 평가·보완 체험

- 예시 아이디어에 1~10점 정수로 점수를 선택할 수 있다.
- 자신의 선택 점수임을 표시하고, 실제 구성원의 집계 점수처럼 표현하지 않는다.
- 보완 의견을 작성해 화면에서 확인한다. 의견은 실제 프로젝트 원문을 변경하지 않는다.
- 점수와 의견은 체험용이며 실제 평가로 접수되지 않는다고 안내한다.
- 체험 점수·의견을 초기화할 수 있게 한다.

### 4.5. 진행·승인 체험

- 예시 아이디어의 검토, 구현 승인, 비용 관련 협업 부서 지정 흐름을 보여 준다.
- ‘진행 단계 보기’, ‘구현 승인 체험’, ‘협업 부서 지정 체험’ 등 실제 처리와 구분되는 문구를 사용한다.
- 실제 승인, 부서 배정, 예산 집행은 발생하지 않는다.
- 실제 팀의 단계 명칭·승인 기준·부서 목록은 `[준비 필요]`다. 흐름 시연에 필요한 단계와 부서는 ‘체험용 예시’로 명시한다.
- 제공된 프로젝트의 실제 진행 상태와 사용자가 조작한 체험 상태를 명확히 구분한다.

## 5. 페이지 구성

한 페이지에서 아래로 내려가며 보는 구성이다. 상단 메뉴와 첫 화면 버튼은 해당 영역으로 이동한다.

| 순서 | 영역 | 주요 내용 |
|---|---|---|
| 1 | 첫 화면 | 한 줄 소개, ‘제안 방법 보기’, ‘과정 체험하기’ 버튼 |
| 2 | 팀 소개 | 팀 역할, 5명 팀원 소개 |
| 3 | 아이디어 제안 안내·작성 체험 | 작성 항목, 실제 제출 경로 안내, 입력과 미리보기 |
| 4 | 예시 아이디어·프로젝트 | 해저 도시 프로젝트 소개, 평가와 보완 체험 |
| 5 | 진행·승인 과정 체험 | 진행 흐름, 구현 승인 및 협업 부서 지정 예시 |
| 6 | 자주 묻는 질문 | 제안 방법, 검토 기준, 체험의 범위 |

휴대폰에서는 메뉴를 접어 표시하고 모든 콘텐츠를 기본 1열로 배치한다.

## 6. 디자인 분위기

사용자가 제공한 **Design System Inspired by Lovable** 자료를 기준으로 한다.

### 색상

| 역할 | 색상 |
|---|---|
| 페이지·카드 기본 배경 | 크림 #f7f4ed |
| 제목·주요 글자·주요 버튼 배경 | 차콜 #1c1c1c |
| 어두운 버튼 글자 | 미색 #fcfbf8 |
| 본문 | rgba(28,28,28,0.82) |
| 보조 설명 | #5f5f5d |
| 카드 테두리·구분선 | #eceae4 |
| 버튼 등 조작 요소의 경계 | rgba(28,28,28,0.4) |
| 호버 배경 | rgba(28,28,28,0.04) |
| 키보드 포커스 | rgba(59,130,246,0.5) 링과 부드러운 그림자 |

### 글자·구성 요소

- 따뜻하고 차분한 분위기, 넉넉한 여백, 읽기 쉬운 글자를 사용한다.
- 제목 굵기는 600, 본문과 버튼은 400을 기본으로 한다.
- 첫 화면 제목은 데스크톱 약 60px, 태블릿 48px, 휴대폰 36px로 조정한다. 한글은 잘리지 않게 자연스럽게 줄바꿈한다.
- 본문은 16px, 소개 문구는 18px, 보조 설명은 14px을 기본으로 한다.
- Camera Plain Variable 자산은 `[준비 필요]`다. 정식 사용 가능한 파일이 없으면 한글에 적합한 Pretendard 또는 시스템 글꼴로 대체한다.
- 카드는 1px 얇은 테두리와 12px 모서리를 사용하며 강한 그림자는 피한다.
- 일반 버튼과 입력란 모서리는 6px, 상태 배지와 필터는 알약 모양을 사용할 수 있다.
- 주요 버튼은 차콜 배경과 은은한 안쪽 그림자를 사용한다.
- 최대 콘텐츠 폭은 약 1200px, 카드 내부 여백은 16~24px, 섹션 간격은 데스크톱 80~128px·휴대폰 약 64px을 기준으로 조정한다.
- 휴대폰 좌우 여백은 16px, 주요 터치 영역은 최소 44px 높이를 확보한다.
- 첫 화면의 옅은 그라데이션은 장식으로만 사용하고, 강한 원색 포인트와 순백 기본 배경은 피한다.
- 팀 로고는 `[준비 필요]`다. 별도 로고가 없으면 팀 이름을 글자로 표시한다.

### 접근성

- 입력란 이름과 필수 여부를 표시한다.
- 오류와 진행 상태를 색상만으로 전달하지 않는다.
- 메뉴, 입력, 평가, 체험 버튼을 키보드로 조작할 수 있게 한다.
- 키보드 포커스가 보이도록 하고 글자와 배경의 명도 차이를 확보한다.
- 예시와 실제 정보, 체험 상태와 실제 진행 상태를 글자로 구분한다.

## 7. 콘텐츠

### 7.1. 팀원 소개

| 구분 | 닉네임 | 담당 역할 |
|---|---|---|
| 팀장 | 캡틴아이디어 (Captain) | 팀 총괄 및 아이디어 기획, 브레인스토밍 진행, 최종 사업 아이템 발굴 방향성 설정 |
| 팀원 1 | 트렌드캐처 (TrendCatcher) | 아이디어 사전 조사, 국내외 신사업 트렌드 및 산업 동향 탐색 |
| 팀원 2 | 팩트체커 (FactChecker) | 시장조사, 고객 불편점 분석, 목표 시장 규모 측정 및 경쟁사 분석 |
| 팀원 3 | 스케치북 (SketchBook) | 아이디어 구현 가능성 조사, 기술적·운영적 실현 가능성과 POC 모델 검토 |
| 팀원 4 | 넥스트스텝 (NextStep) | 사업화 시나리오 검증 및 테스트 결과 데이터 정리 |

POC는 아이디어가 실제로 가능한지 작은 규모로 시험하는 ‘개념 검증’을 뜻한다. 팀원 사진·개별 소개 이미지가 필요하다면 `[준비 필요]`이며, 임의의 사진이나 실명을 만들지 않는다.

### 7.2. 소개 프로젝트

**프로젝트명: 해수면 상승에 대응하는 해저 도시 프로젝트**

| 항목 | 사용자 제공 내용 |
|---|---|
| 기획 배경 | 기후 변화로 인한 해수면 상승 문제에 대응하여 지속 가능한 새로운 인류 거주 공간을 탐색한다. |
| 주요 내용 | 수중 기압 조절 및 자급자족 에너지(태양광·해류 발전) 시스템 기반의 해저 주거 캡슐 모듈을 설계하는 구상이다. |
| 시장성 및 검증 계획 | 해양 생태계 영향 최소화 모델 검증 및 초기 해중 연구 기지 형태의 POC 시나리오 수립을 다룬다. |

이 내용은 제공된 프로젝트 구상이다. 기술적 실현 가능성이나 시장성이 검증되었다는 표현을 사용하지 않는다.

- 실제 진행 단계: `[준비 필요]`
- 검증 수행 여부 및 결과: `[준비 필요]`
- 실제 시장 규모·수요·경쟁 분석 자료: `[준비 필요]`
- 예상 비용·일정·승인 여부·협업 부서: `[준비 필요]`
- 프로젝트 이미지 및 출처: `[준비 필요]`

평가·보완·승인 체험에 이 프로젝트를 활용할 수 있으나 체험에서 발생한 점수·의견·상태는 실제 프로젝트 기록과 구분한다.

### 7.3. 자주 묻는 질문

**아이디어는 어떻게 제안하나요?**

제목, 해결하려는 문제, 아이디어 설명, 기대 효과를 정리합니다. 예상 비용과 구현 방법은 아는 범위에서 선택해 작성합니다. 홈페이지에서는 작성과 미리보기를 체험할 수 있습니다. 실제 제출 경로는 `[준비 필요]`입니다.

**어떤 기준으로 가능성을 검토하나요?**

최초아이디어팀은 아이디어 기획, 구현 가능성 검토와 시장조사를 담당합니다. 공식 검토 기준과 승인 절차는 `[준비 필요]`입니다.

**체험에서 입력하면 팀에 전달되나요?**

아니요. 점수·의견·제안 내용은 전송되거나 여러 사람에게 공유되지 않습니다. 승인과 부서 지정도 체험이며 실제 업무 처리가 아닙니다.

**프로젝트의 실제 진행 상황을 알 수 있나요?**

확인된 정보만 소개합니다. 현재 실제 단계와 검증 결과는 `[준비 필요]`이며, 체험 화면의 상태는 실제 진행 현황을 뜻하지 않습니다.

## 8. 만들지 않을 것

- 로그인·회원가입과 사용자 계정 관리.
- 데이터베이스 및 여러 사람의 입력 내용을 공동 저장하는 기능.
- 실제 아이디어 접수·전송, 메일 발송, 외부 서비스로의 입력 전송.
- 실제 경영진 승인, 실제 협업 부서 배정과 예산 집행.
- 실제 검증 결과처럼 보이는 가상의 점수·성과·시장 수치.
- 제공되지 않은 팀 정보·프로젝트 결과·사진·로고를 사실처럼 만들어 넣는 작업.

체험 입력값을 분석 도구 등 외부 서비스에 보내지 않는다. 향후 실제 공동 업무 도구가 필요하면 별도 범위로 기획한다.

## 9. 구현·배포 조건

- 기본 파일은 `index.html`, 필요에 따라 CSS·JS와 이미지 파일을 분리한다.

- 배포된 주소에서도 메뉴·파일·체험 기능이 정상 동작해야 한다.

## 10. 완료 기준

아래 기준은 합의한 요구사항을 확인하기 위한 검토안이다. 구현 후 실제 화면과 배포 주소에서 확인한다.

- [ ] 팀 이름, 확정한 한 줄 소개, 팀장 포함 5명의 닉네임과 역할이 정확하다.
- [ ] 합의한 6개 영역이 정한 순서로 표시되고 메뉴와 첫 화면 버튼이 해당 영역으로 이동한다.
- [ ] 제안 안내에서 필수 4개 항목과 선택 2개 항목이 구분된다.
- [ ] 필수 입력 누락을 안내하고 작성한 내용을 미리 볼 수 있다.
- [ ] 평가 체험에서 1~10점 선택이 가능하며 자신의 체험 점수임을 표시한다.
- [ ] 보완 의견을 작성·확인하고 체험 점수와 의견을 초기화할 수 있다.
- [ ] 진행·승인·협업 부서 지정 화면에 ‘체험용’ 표시가 있으며 실제 업무 처리로 오해할 문구가 없다.
- [ ] 해저 도시 프로젝트의 구상과 검증 계획이 정확하게 소개되고, 미확인 결과는 `[준비 필요]`로 남아 있다.
- [ ] 로그인·데이터베이스·실제 제출·외부 입력 전송 기능이 없다.
- [ ] 크림 배경, 차콜 글자, 얇은 테두리, 넉넉한 여백의 디자인이 일관된다.
- [ ] 휴대폰 375px, 태블릿, 데스크톱에서 글자·입력·버튼이 잘리지 않고 가로 스크롤이 없다.
- [ ] 키보드로 주요 기능을 사용할 수 있고 포커스와 오류 안내가 보인다.
- [ ] GitHub에 최종 소스가 올라가 있고 Vercel 배포 주소에서 홈페이지와 체험 기능이 동작한다.
