# 기획팀 작업용 필터 — 업무 도구 기획서

## 한 줄 소개
들어온 요건을 정리하고 화면별 수정 영역과 반영 초안을 구체화하는 기획자용 작업 도구.

이 문서는 최초 기획 기준이다. 제출 HTML에는 이후 피그마 REST API 읽기 및 JSON 변환 기능이 추가되어 있다. 실제 계정·파일 연결 결과는 사용자 환경에서 확인해야 한다.

## 1. 풀 문제
요건이 들어올 때마다 피그마에서 영향을 받는 화면과 영역을 찾고, 가입 유형별 조건을 정리해 작업 지시로 옮겨야 한다. 이 탐색과 정리 과정에서 적용 누락을 줄인다.

| 항목 | 지금 | 목표 |
|---|---|---|
| 화면 탐색 | 피그마 화면을 직접 확인 (가정) | 근거가 있는 화면·영역 후보 제시 |
| 요건 정리 | 요청 문장을 작업 지시로 변환 | 조건표와 반영 초안 생성 |
| 검토 | 화면별 적용 누락 확인 | 적용 대상·제외 대상·미확인 항목 구분 |
| 시간 | 측정 전 | 동일 요건의 수작업과 비교해 측정 |

## 2. 사용자 · 사용 장면
- 기획자가 변경 요건을 접수한 직후 사용한다.
- 첫 버전은 개인용 PC 브라우저 화면으로 가정한다.
- 최종 목표는 피그마 화면 분석이다. 실제 피그마 파일은 아직 제공되지 않았으므로 특정 화면을 찾았다고 주장하지 않는다.

## 3. 이상적인 시작 화면
“요건과 화면 자료를 넣으면 수정 후보 영역과 이유가 보이고, 나는 적용 범위를 검토하고 초안을 다듬는다.”

## 4. 화면 모듈 (최대 3개)
| 모듈 | 기능 | 필요한 이유 |
|---|---|---|
| A. 요건 입력 | 요청 원문, 조건, 예외, 화면 자료 입력 | 문장 속 변경 대상과 조건 분리 |
| B. 영향 화면·영역 | 화면명, 영역명, 노드 ID, 근거, 확인 상태 표시 | 수정 위치 탐색과 누락 검토 |
| C. 반영 초안 | 조건표, 작업 지시, 확인할 질문, 검수 항목 생성·편집·복사 | 검토 가능한 작업 명세 작성 |

## 5. 화면 배치
```text
상단: 기획팀 작업용 필터 · 자료 연결 상태 · 백업/복원
왼쪽: A. 요건과 화면 자료
오른쪽: B. 영향 화면·영역 목록
하단: C. 반영 초안 / 조건표 / 검수 항목
```
휴대폰에서는 A → B → C 순서로 표시한다.

## 6. 데이터
| 모듈 | 필드 | 종류 | 필수 | 예시 |
|---|---|---|---|---|
| A | 요청 ID·제목·원문 | 글 | O | REQ-DEMO-001 / 수신 방법 노출 조건 변경 |
| A | 조건표 | 목록 | O | 기기변경: 숨김, 번호이동·신규가입: 표시 |
| A | 화면 자료 | JSON | 분석 시 O | 가상 화면 목록 또는 노드 자료 |

## 7. 기능 상세와 예시 요건
사용자 제공 원문: “일괄적으로 기기변경은 요금안내서 수신 방법 비노출, 번이 / 신규는 노출.”

‘번이’는 번호이동, ‘신규’는 신규가입으로 표기를 통일한다.

| 가입 유형 | 요금안내서 수신 방법 영역 |
|---|---|
| 기기변경 | 비노출 |
| 번호이동 | 노출 |
| 신규가입 | 노출 |
| 미선택·그 외 | 요건 미정: 확인 필요 |

### 화면 탐색
- 제공한 화면 자료에서 ‘요금안내서’, ‘수신 방법’ 및 관련 표현을 검색한다.
- 일치 텍스트의 상위 화면과 영역을 후보로 묶고 원문 근거를 표시한다.
- 한 화면에서 찾았다는 이유로 전체 적용이 끝났다고 표시하지 않는다. 읽은 자료 범위와 미확인 화면을 밝힌다.
- 후보가 없으면 ‘제공 자료 내 일치 항목 없음’을 표시한다. 존재하지 않는 화면·노드 ID를 만들지 않는다.
- 가상 데이터는 ‘예시’로 표시하고 실제 분석 결과와 구별한다.

### 반영 초안
“제공 자료에서 확인한 ‘요금안내서 수신 방법’ 영역에 가입 유형별 노출 조건을 적용한다. 기기변경은 숨기고 번호이동·신규가입은 표시한다. 관련 화면마다 적용 여부를 확인한다.”

다음은 확정 요건으로 처리하지 않고 확인할 질문으로 남긴다.
- ‘일괄’에 포함되는 상품·채널·가입 경로·PC/모바일 범위는 어디까지인가?
- 기기변경에서 기존 선택값을 유지할지 초기화할지, 서버 전달값은 어떻게 할지?
- 비노출 시 필수 입력 검증을 제외할지? 기본 수신 방법은 어디서 결정하는지?
- 가입 유형을 바꿀 때 값 복원·초기화 규칙은 무엇인지?
- 확인·완료 화면이나 요약 영역에도 같은 조건을 적용할지?

초안은 확정 규칙과 미확정 항목을 분리하고 사용자가 수정·복사할 수 있게 한다.

## 8. 범위와 연동 방식
### 먼저 시험할 버전 (가정)
- 로컬 HTML 한 파일로 요건 입력, 구조화된 화면 JSON 가져오기, 텍스트 기반 후보 검색, 조건표·작업 문구 생성을 구현한다.
- 제공된 예시 요건의 조건표는 규칙 기반으로 처리한다. 임의의 자연어를 이해하는 AI 기능으로 소개하지 않는다.
- JSON에는 화면명, 영역명, 텍스트, 노드 ID, 선택적 링크를 포함한다. 피그마 원본 JSON과 내부 입력 형식은 다르므로 변환 단계가 필요하다.
- 링크 입력만으로 피그마를 읽거나 이미지를 시각 분석하지 않는다. 링크는 출처로 보관한다.
- JSON 백업·복원과 예시 지우기를 제공한다.

### 실제 피그마 자동 분석 단계
- 피그마 연결 도구 또는 인증된 API로 파일·노드 정보를 읽는 기능을 별도로 구현한다.
- 연결 권한과 실제 파일을 확인한 후 사용 가능한 텍스트·트리·이미지 범위를 정한다.
- 의미 기반 분석에는 모델 연결과 별도 실행 환경이 필요하다. 로컬 HTML에 비밀 키를 저장하지 않는다.
- 이 단계는 연결 기능을 구현하고 실제 파일로 검증한 뒤에만 ‘자동 분석 가능’으로 표시한다.

첫 버전 범위 밖: 피그마 직접 수정, 서버·로그인·팀 공유, 임의 요건의 AI 분석.

## 9. 디자인
사용자가 제공한 Figma 디자인 문서(DESIGN.md)를 기준으로 흰 바탕, 검정 알약형 버튼, 라임색 결과 블록과 넓은 여백을 적용한다. 전용 글꼴 대신 시스템 기본 글꼴을 사용한다. 정확한 색상 값이 없는 라임은 #d5f37f 근삿값을 사용한다. 확인 완료·후보·미확인은 글자로 구별한다.

## 10. 기술 조건·저장
- 첫 버전은 CSS·JS를 포함한 index.html 한 파일이며 더블클릭으로 연다.
- 브라우저 localStorage에 저장하고 읽기·쓰기는 try/catch로 처리한다.
- 브라우저 데이터 삭제 시 기록이 사라질 수 있으므로 JSON 백업·복원을 제공한다.
- 로컬 시험 버전은 외부로 데이터를 전송하지 않는다. 예시는 가상 자료를 사용한다.

## 11. 완료 기준
- 기기변경=비노출, 번호이동·신규가입=노출이 조건표와 초안에서 일치한다.
- 각 후보에 제공 자료의 출처·노드·일치 근거가 있고 실제 피그마 분석으로 오인하지 않는다.
- 일치 항목 없음·잘못된 JSON·저장 실패를 처리한다.
- 미정인 가입 유형과 검증·값 처리 규칙을 임의로 확정하지 않는다.
- 기록 저장·새로고침·백업·복원 후 내용이 유지된다.
- 375px 너비에서 가로 스크롤 없이 사용할 수 있다.
