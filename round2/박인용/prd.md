# 구매팀 소개 페이지 PRD

| 항목 | 내용 |
|---|---|
| 문서 상태 | 초안 v0.2 · 첨부 디자인 참고 반영 · 검토용 |
| 작성일 | 2026-11-06 |
| 작성자 | 구매팀 (연습용) |
| 관련 문서 | logo-prompt.md, build-plan.md |

PRD(Product Requirements Document)는 무엇을, 누구를 위해, 왜 만드는지 정리한 기획서입니다.

## 1. 배경 · 문제
- 구매를 단순히 물건을 사는 일로 이해해 전략적 역할이 잘 드러나지 않는다.
- 현업 부서와 협력업체가 구매 절차와 담당자를 쉽게 확인할 안내가 필요하다.
- SI 관련 구매를 전략적으로 수행하는 3명 규모의 팀을 소개한다. 인원은 사용자 답변의 예시를 기준으로 한 가정이다.

## 2. 목표와 성공 기준
| 목표 | 성공 기준 (검토 방법, 가정) |
|---|---|
| 절차와 담당자를 빠르게 찾는다 | 검토자 3명이 첫 화면에서 두 바로가기를 찾아 해당 안내에 도달한다 |
| 구매팀의 전략적 역할을 이해한다 | 검토자가 구매팀 역할을 가격 외 요소 2개 이상을 포함해 설명한다 |
| 요청 준비에 필요한 정보를 확인한다 | 검토자가 절차 안내를 보고 준비 자료와 문의 경로를 찾는다 |

## 3. 대상 사용자
| 대상 | 궁금한 것 | 페이지가 줘야 할 답 | 기대 행동 |
|---|---|---|---|
| 구매를 요청하는 현업 부서 | 언제, 누구에게, 무엇을 준비해 요청하나 | 절차, 준비 자료, 업무별 담당 역할 | 절차·담당자 확인 |
| 협력업체 | 어떤 절차로 협의하고 누구에게 문의하나 | 협의 흐름, 역할별 문의 경로 | 절차·담당자 확인 |

## 4. 범위
이번 범위: 한 장짜리 소개 페이지, 메뉴 6개, 구매 절차·담당자 바로가기, 업무 카드 6개, FAQ, 예시 문의 경로.

범위 밖: 로그인, 구매 요청 접수·승인 시스템, 견적 업로드, 실제 발주·계약 처리, 서버 전송 문의 폼. 내부 자료와 실제 연락처는 사용하지 않는다.

## 6. 화면 구성 (위에서 아래로)
```
[고정 헤더: 구매팀 글자 로고 + 메뉴]
① 첫 화면: 한 줄 소개 + [구매 절차 확인] [담당자 찾기]
② 구매 절차: 단계별 흐름과 준비 자료
③ 담당자 안내: 역할별 카드 3개
④ 팀 소개: 전략적 구매의 가치
⑤ 하는 일: 업무 카드 6개
⑥ 자주 묻는 질문
⑦ 문의
[푸터]
```
메뉴 순서는 사용자가 고른 순서를 유지하고, 본문은 절차·담당자 확인 목적에 맞춰 배치한다.

### 데스크톱의 카탈로그형 배치
- 페이지 전체를 검정 프레임으로 감싸고 가운데 정렬한다. 콘텐츠 최대 폭은 1160px로 한다.
- 상단에는 검정 배너와 흰색 '구매팀' 로고, 짧은 소개를 표시한다.
- 첫 화면 아래는 왼쪽 약 28% 안내 영역, 오른쪽 약 72% 상세 영역의 2단 구성으로 한다.
- 왼쪽 안내 영역에는 '구매 전, 먼저 확인하세요' 메시지와 구매 절차·담당자 바로가기를 담는다.
- 오른쪽 상세 영역에는 위에서 정한 본문 순서대로 절차·담당자·소개·업무·FAQ·문의를 배치한다.
- 768px 이하에서는 안내 영역이 본문 위로 이동한다. 문서 읽기 순서와 키보드 이동 순서도 화면 순서에 맞춘다.

## 7. 콘텐츠 상세
### 7-1. 첫 화면과 팀 소개
- 제목: 구매의 기준을 세우고, 프로젝트의 가치를 높입니다.
- 보조 문구: SI 구매의 비용·품질·납기·계약 위험을 함께 검토하는 구매팀입니다.
- 버튼: 구매 절차 확인 → #process / 담당자 찾기 → #people.
- 팀 소개: 필요한 것을 사는 일을 넘어, 요구사항과 공급 조건을 비교하고 프로젝트에 맞는 구매 방안을 설계합니다.
- 제목·설명은 사용자의 답변을 바탕으로 제안한 문구이며 수정 가능하다.

### 7-2. 업무 카드
설명과 요청 예시는 가정이며 실제 업무 범위에 맞춰 검토한다.

| # | 제목 | 설명 | 요청 예시 |
|---|---|---|---|
| 1 | 구매 전략 수립 | 프로젝트 요구와 일정에 맞는 구매 방향을 설계합니다. | 프로젝트 초기 구매 계획을 함께 세우고 싶어요. |
| 2 | 견적 비교 | 가격과 범위, 조건을 같은 기준으로 비교합니다. | 제안별 견적의 차이를 확인하고 싶어요. |
| 3 | 가격·계약 협상 | 가격과 거래 조건을 검토하고 협의합니다. | 가격과 계약 조건 협의가 필요해요. |
| 4 | 협력업체 선정 | 수행 역량과 공급 조건을 종합적으로 검토합니다. | 요구사항에 맞는 협력업체 검토가 필요해요. |
| 5 | 발주·납기 관리 | 발주부터 공급 일정까지 진행 상황을 확인합니다. | 프로젝트 일정에 맞춰 납기를 확인하고 싶어요. |
| 6 | 하도급 리스크 관리 | 거래 과정의 위험 요소와 관련 검토 필요 사항을 확인합니다. | 계약 전에 거래 구조와 검토 항목을 확인하고 싶어요. |

### 7-3. 구매 절차 (전 단계 가정)
| 단계 | 안내 |
|---|---|
| 1. 사전 상담·요청 | 목적, 범위, 예산, 희망 일정을 정리합니다. |
| 2. 요구사항·구매 전략 검토 | 사양과 공급 조건, 구매 방안을 검토합니다. |
| 3. 견적 비교·업체 검토 | 비용, 수행 역량, 일정 등을 비교합니다. |
| 4. 조건 협의·계약 검토 | 가격, 납기, 계약 조건과 위험 요소를 확인합니다. |
| 5. 내부 승인·발주 | 필요한 내부 절차를 확인하고 발주합니다. |
| 6. 납기·이행 확인 | 공급·수행 상황과 후속 사항을 확인합니다. |

준비 자료 예시: 구매 목적, 요구 범위·사양, 희망 일정, 예산 범위, 보유 견적. 실제 승인 체계·필수 서류·소요 기간은 미정이다. 화면에 '예시 절차 · 실제 진행 전 담당자 확인'을 표시한다.

### 7-4. 담당자 안내 (가상의 역할 배분)
| 표기 | 담당 역할 | 문의 예시 |
|---|---|---|
| 담당 A | 구매 전략·사전 상담 | 요청 방향과 준비 자료 |
| 담당 B | 견적 비교·업체 선정·협상 | 견적과 거래 조건 |
| 담당 C | 발주·납기·하도급 리스크 검토 연계 | 진행 상황과 추가 검토 |

위 배분은 실제 담당 체계가 아닌 가정이다. 실명·실제 연락처 대신 역할 표기를 사용하고, 각 카드는 문의 섹션으로 연결한다.

### 7-5. FAQ
- **구매는 단순히 사기만 하면 되는 것 아닌가요?** 구매팀은 가격뿐 아니라 품질, 납기, 공급 역량과 계약 위험을 함께 검토해 프로젝트에 맞는 선택을 돕습니다.
- **언제 구매팀에 문의하면 되나요?** 요구사항과 일정이 정리되기 시작할 때 사전 상담하는 흐름을 제안합니다. 실제 요청 시점과 소요 기간은 담당자에게 확인합니다. (가정)
- **무엇을 준비하면 되나요?** 목적, 요구 범위, 희망 일정, 예산과 보유 견적을 준비하는 방안을 제안합니다. 필수 서류는 담당자에게 확인합니다. (가정)
- **협력업체는 어디로 문의하나요?** 문의 섹션의 예시 경로를 확인하도록 안내합니다. 실제 업체 등록·접수 경로는 미정입니다. (가정)

### 7-6. 문의
| 항목 | 값 |
|---|---|
| 요청 채널 | #구매문의 (예시, 연결하지 않는 텍스트) |
| 이메일 | team@example.com (예시, 실제 발송 링크 없음) |
| 응답 시간 | 준비 중 · 확정 시 안내 |

문의 정보는 예시임을 표시한다. 실제 접수가 가능한 것처럼 보이는 입력 폼은 두지 않는다.

| 포인트 색 | #404040, 무채색만 사용 |

| 로고 | 우선 '구매팀' 글자 로고, 추후 images/logo.png로 교체 |
| 참고 자료 | 사용자가 첨부한 Dell 1996 디자인 분석 문서. 이미지 없이 문서의 구조적 특징을 재해석 |

### 8-1. 첨부 문서의 구매팀 적용 기준
참고 자료는 1996년 Dell 홈페이지의 디자인 분석이다. 문서 속 브랜드 전용 규칙·연락처·상품 정보는 참고 대상의 설명이며 이 홈페이지의 요구사항이 아니다.

| 참고 특징 | 구매팀 적용 |
|---|---|
| 두꺼운 검정 외곽 프레임 | 데스크톱 8px, 태블릿 4px, 휴대폰 2px 프레임 |
| 검정 상단 배너 | 구매팀 로고와 전략적 구매 메시지 |
| 왼쪽 안내·오른쪽 카탈로그 | 왼쪽 빠른 안내, 오른쪽 절차·역할·업무 상세 |
| 흰 제목 띠 + 색 면의 리본 카드 | 흰 제목 띠 + 검정 구분선 + 연회색 본문. 업무·절차 카드에 적용 |
| 굵은 대제목과 밀도 있는 편집 | 큰 한글 고딕 제목, 짧은 설명과 명확한 번호. 본문은 16px 이상, 줄 높이 1.65 |
| 컬러 스티커·판매 버튼 | 무채색 '바로 확인' 라벨과 절차·담당자 버튼 |
| 상품 사진이 카드 오른쪽에 걸친 구성 | 역할에 맞는 번호·문서·비교표 형태의 단순 인라인 SVG로 변형 |
| 하단 아이콘 내비게이션 | 절차 / 담당자 / FAQ / 문의의 텍스트와 단순 아이콘 링크 |

구매팀의 흑백 선택을 유지한다. Dell 로고·상품·전화번호·수상 배지는 사용하지 않는다. 다색 카드·빨간 판매 패널은 흑백 명도 차이로 바꾼다. 한글 본문은 시스템 고딕을 우선하고, 영어 보조 라벨만 Arial Black 계열을 사용할 수 있다. 장식보다 업무 탐색을 우선하며 페이지 구조는 시맨틱 HTML과 CSS Grid로 구현한다.

## 9. 반응형 · 접근성
- 375px 휴대폰과 1280px 데스크톱에서 가로 스크롤 없음.
- 업무 카드: 데스크톱 3열 → 태블릿 2열 → 휴대폰 1열.
- 640px 미만에서 햄버거 메뉴, 열림 상태와 키보드 조작 지원.
- 768px 이하에서는 좌우 2단을 1단으로 전환하고, 휴대폰 본문 좌우 여백은 16px로 한다. 버튼은 높이 44px 이상으로 한다.
- 고정 헤더에 제목이 가려지지 않도록 이동 여백 적용.
- 충분한 명도 대비, 보이는 키보드 초점, 이미지 대체 텍스트 제공.
- FAQ는 기본 details/summary 요소를 사용한다. 움직임 최소화 설정을 존중한다.

## 10. 기술 조건
- index.html 하나에 CSS·JS 포함. 빌드 도구 없이 더블클릭으로 연다.
- 글꼴 외 외부 의존 최소화. 서버, 로그인, 데이터 수집 없음.
- 로고 파일이 없으면 첫 글자 '구'의 인라인 SVG와 '구매팀' 텍스트를 표시한다. 추후 images/logo.png 파일이 추가되면 이미지로 표시되도록 처리한다.
- 하도급 관련 법령·기한·적법성 판단은 제공하지 않고 팀의 검토 역할만 소개한다.
